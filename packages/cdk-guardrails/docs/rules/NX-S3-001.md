# NX-S3-001 — En `prod` todo bucket: versioning, bloqueo público completo y TLS obligatorio

| | |
|---|---|
| **Severidad** | `error` |
| **Aplica en** | `prod` |
| **Excepción** | Sí (declarada dos veces, con caducidad) |
| **Falla cerrado** | Sí (caso «no resoluble») |

## Qué verifica

Todo `AWS::S3::Bucket` tiene, a la vez:

1. `VersioningConfiguration.Status: Enabled`.
2. `PublicAccessBlockConfiguration` con **los cuatro** flags en `true` (`BlockPublicAcls`, `BlockPublicPolicy`, `IgnorePublicAcls`, `RestrictPublicBuckets`).
3. Un `AWS::S3::BucketPolicy` (su `Bucket` apunta al bucket) con una sentencia que **niega el transporte inseguro**: `Effect: Deny`, `Principal` comodín, `Action` `s3:*` (o `*`), `Condition.Bool.aws:SecureTransport = false` y `Resource` que cubre el bucket **y** sus objetos (`…/*`). Es la forma que genera `enforceSSL: true` de CDK.

**No resoluble (falla cerrado):** un valor de 1 o 2 que sea un intrinsic, o una política del bucket cuyo `PolicyDocument` no se pueda leer, se **reportan** con «no se puede comprobar».

### Exención de los buckets de logs de acceso (criterio decidido)

Un bucket queda **exento solo del versioning** si **el propio app lo usa como destino de logs de acceso**: el atributo `access_logs.s3.bucket` de un ALB, `AccessLoggingPolicy.S3BucketName` de un CLB, `DistributionConfig.Logging.Bucket` de CloudFront o `LoggingConfiguration.DestinationBucketName` de otro bucket (las referencias se siguen entre stacks por `Ref`, export y parámetros SSM).

- **Por qué estructural y no un tag o un prefijo:** un tag declarado se puede poner en cualquier bucket de datos para esquivar la regla; que el app **use** el bucket como destino de logs es un hecho del template que no se falsifica sin cambiar la infraestructura.
- **Por qué solo el versioning:** un bucket de logs con retención corta acumularía versiones no actuales a costo y sin valor. El bloqueo de acceso público y el TLS obligatorio se le **siguen exigiendo**.
- Un bucket de logs cuyo consumidor vive **fuera del app** no queda exento: se corrige o lleva una excepción declarada.

## Por qué

- **Versioning:** un borrado o una sobreescritura accidental (o maliciosa) es recuperable.
- **Bloqueo público completo:** la mayoría de las filtraciones de datos en S3 son un bucket expuesto por una ACL o una política.
- **TLS obligatorio:** sin el `Deny`, un cliente puede hablar con el bucket en claro.

## Cómo corregirlo

```ts
new s3.Bucket(this, 'Data', {
  versioned: true,
  blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
  enforceSSL: true,
});
```

Un bucket público a propósito (sitio web estático) o efímero lleva una excepción declarada dos veces, con motivo, dueño y caducidad.

## De dónde viene

Estándar de almacenamiento de producción. La forma del `Deny` es la que emite `enforceSSL` de CDK, verificada contra un synth real.

## Límites conocidos

- Solo reconoce la sentencia estándar de `enforceSSL`. Una política equivalente escrita de otra forma (p. ej. con `NotAction`) se reporta: reescríbala con la forma estándar o declare la excepción.
- No juzga el cifrado, el ciclo de vida ni el `DeletionPolicy` del bucket.
- Los buckets creados por constructs de CDK (staging de assets, `BucketDeployment`) son buckets del template como cualquier otro.
